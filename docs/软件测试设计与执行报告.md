## 1 测试对象与范围

### 1.1 被测系统（SUT）

工作台是一个 Electron 应用，三层结构：

```
渲染进程（renderer/index.html）   ← 界面：按钮卡片、输出区、拖拽旋转

        ↕
```

## 3 白盒测试（第 2 题）

### 3.1 被测代码

`lib/resolve-run.js` 的 `resolveRun()`——决定"命令在哪个目录里跑"。选它做白盒有三个原因：纯函数（零依赖、可注入 `exists`）、判定密集（4 个判定 + 2 个三元）、是 `wb:run` 的核心逻辑。

```js
 1  function resolveRun(o) {
 2    const opts = o || {};                                       // S1
 3    const command = String(opts.command == null ? '' : opts.command);  // S2（三元 T1）
 4    const pkgDir = opts.pkgDir ? String(opts.pkgDir) : '';      // S3（三元 T2）
 5    const exists = opts.exists || (() => true);                 // S4（短路）
 6    if (!command.trim()) return { ok:false, error:'这个动作没有声明命令' };  // D1 / S5
 7    let cwd = pkgDir || undefined;                              // S6
 8    let source = 'package';                                     // S7
 9    if (opts.cwd !== undefined && opts.cwd !== null && String(opts.cwd).trim() !== '') {  // D2（a,b,c）
10      const p = String(opts.cwd).trim();                        // S8
11      cwd = isAbsolutePath(p) ? p                               // D3
12            : (pkgDir ? pkgDir + '\\' + p.replace(/^[\\/]+/,'') // D4 / S9b
13                      : p);                                     // S9c
14      source = 'cwd';                                           // S10
15    }
16    if (cwd && !exists(cwd)) return { ok:false, error:'工作目录不存在：'+cwd };  // D5（a,b）/ S11
17    return { ok:true, cwd, source };                            // S12
18  }
19
20  function isAbsolutePath(p) {                                  // S13
21    const s = String(p || '');
22    return /^[a-zA-Z]:[\\/]/.test(s) || s.startsWith('\\\\') || s.startsWith('/');   // D6（三个或条件）
23  }
```

## 4 集成测试：桩与驱动（第 3 题）

### 4.1 为什么必须用桩和驱动

工作台一次真实运行要：开 Electron 窗口 → 连渲染进程 → 起真实子进程 → 收真实输出。把它塞进自动化测试有三个不可控点：

1. **不可控**：子进程什么时候输出、以什么退出码结束，无法在断言里指定；
2. **不可重复**：真实命令（`start shell:MyComputerFolder`）会弹出资源管理器；
3. **不可观测**：主进程"内部到底有没有起进程、起在哪个目录"，只能从界面反推。

于是采用 **桩（stub）+ 驱动（driver）**：

```
        ┌──────────────── 驱动 driver ────────────────┐
        │  test/lib/harness.js 的 boot()               │
        │  · 加载真实 main.js                          │
        │  · 收集它注册的 13 个 ipcMain 通道            │
        │  · invoke(channel, …) 扮演"界面"              │
        └──────────────────┬──────────────────────────┘
                           │ 调用
        ┌──────────────────▼──────────────────────────┐
        │           真实 main.js（被测对象）            │
        └──────────────────┬──────────────────────────┘
                           │ require
        ┌──────────────────▼──────────────────────────┐
        │  桩 stub：假 electron + 假 child_process      │
        │  · 假窗口 / 假对话框 / 假协议                 │
        │  · 假子进程：可随时 emit stdout / exit(code)  │
        │  · exec 只记录 taskkill 命令                  │
        └─────────────────────────────────────────────┘
```

`main.js` **一个字节都没有为测试而修改**——桩通过拦截 `Module._load` 注入，测的仍然是真实主进程逻辑与真实文件系统，只有"外部世界"是假的。

### 4.2 桩清单

| 被桩替换的真实依赖 | 假实现提供什么 | 为什么 |
|---|---|---|
| `electron.app` | `getPath('userData')` → 临时目录；`whenReady()` 立即 resolve；记录 `app.on` 钩子 | 隔离真实用户数据；能断言"关窗回收"钩子是否注册 |
| `electron.BrowserWindow` | 假窗口：记录 `destroyed / minimized / maximized`，`webContents.send` 把消息收进事件数组 | 不开真窗口，同时能观察主进程推给界面的每一条消息 |
| `electron.ipcMain` | `handle(channel, fn)` 把 fn 存进表 | 让测试可以"扮演界面"直接调用通道 |
| `electron.dialog` | `showMessageBoxSync` 返回预设值；`showOpenDialog` 返回预设路径 | 可控地模拟"用户点覆盖/取消""用户选了某个目录" |
| `electron.shell` | `openPath` 只记录 | 不真的打开资源管理器 |
| `electron.protocol` | 捕获 `wsp://` 处理器，供测试直接喂 URL | 不启动真实渲染进程也能测协议安全 |
| `child_process.spawn` | 假子进程（EventEmitter + 假 pid），测试可 `emitStdout/emitStderr/emitExit(code)` | 输出与退出码完全可控，且能记录"命令原文 + 工作目录" |
| `child_process.exec` | 只把命令记进 `execCalls` | 断言停止时是否真的 `taskkill /T /F` |

## 5 缺陷与设计风险清单

测试过程中发现的问题（按严重度排序）。**这些是真实结论，不是"全绿就没问题"。**

| 编号 | 严重度 | 位置 | 问题 | 证据 | 建议 |
|---|---|---|---|---|---|
| **D-1** | 中 | `lib/resolve-run.js:57` | `p.replace(/^[\\/]+/, '')` 是**不可达代码**：以 `/` 或 `\` 开头的字符串都会被 `isAbsolutePath` 判成绝对路径，永远走不到相对分支的拼接。副作用是 Windows 用户写 `cwd: "/tools"` 会被当成 Unix 绝对路径 `/tools`，直接报"工作目录不存在" | 用例 **WB12** 实测：`{cwd:'/tools', pkgDir:'C:\pkg'}` → `{ok:false, error:'工作目录不存在：/tools'}` | 删除不可达的 `replace`，或在判断绝对路径前按平台归一化（`path.win32.normalize`） |
| **D-2** | 中 | `main.js: runAction` | **主进程不做"同一动作不可重复启动"的判定**，防重入完全依赖渲染层 `runOf` 表。若插件界面连发两条 `run` 消息，主进程会起两个进程（NFR-7 只在界面层成立） | 代码走查 + `runs` 以 `runId` 为键，无 `actionId` 去重 | 在 `runAction` 里按 `actionId` 查重，把不变量下沉到主进程 |
| **D-3** | 低 | `lib/resolve-run.js:50` | `pkgDir` 为空串时返回 `cwd: undefined`（用例 **WB17**），此时 `spawn` 会用主进程的当前目录，行为不确定 | WB17：`{command:'echo hi'}` → `{ok:true, cwd:undefined}` | 主进程对 `cwd === undefined` 做显式兜底（用 `app.getPath('userData')` 或直接拒绝） |
| **D-4** | 低 | `main.js` 两层校验 | `wb:run` 只做真值判断（`!spec.command`），纯空白命令要到 `resolveRun` 才被拦下，两层提示语不一致（"缺少命令" vs "这个动作没有声明命令"） | 用例 BV13 / BV14 分别命中两条不同错误文案 | 统一为一条错误契约，或把 trim 校验提前 |
| **D-5** | 信息 | `main.js: registerWorkspaceProtocol` | 目录穿越有两道防线，但两条路径返回的状态码不一致（URL 规范化 → 400；`path.resolve` 白名单 → 403） | 用例 I-22（403）与 I-22b（400） | 安全上没问题；若前端要区分提示，可统一为 403 |
| **D-6** | 信息 | `main.js: uninstall` | 卸载内置工作区时返回 `deleted:false`，但没有区分"内置不可卸载"与"删除失败"两种语义 | 用例 I-20 | 返回值加 `reason` 字段 |

**另有 3 项不在自动化范围、需人工验收的检查点**（界面层）：
① 拖动分界线改尺寸后重启软件是否保持（FR-11）；② 运行中每秒重绘卡片是否导致 hover 抖动；③ 自定义界面 iframe 在真实沙箱下能否加载 `wsp://` 资源。

## 6 结论

| 题目 | 要求 | 交付情况 |
|---|---|---|
| **1** | 四种黑盒方法（等价类、边界值、因果图、决策表）设计测试用例 | ✅ 等价类 15 个类 / 18 条用例，边界值 18 条，因果图 1 张（6 因 5 果 + 3 类约束），决策表 2 张共 9 条规则，全部自动化执行通过 |
| **2** | 两种白盒方法（逻辑覆盖、基本路径）设计测试用例 | ✅ 逻辑覆盖五级全达标（判定/条件覆盖矩阵自动自检 100%），基本路径按 `V(G)=6` 覆盖 6 条独立路径 + 1 条补充；被测模块行覆盖 **100%**，主进程行覆盖 **95.0%** |
| **3** | 用桩和驱动完成集成测试 | ✅ 7 类桩 + 1 个驱动接口，32 条集成用例覆盖"扫描→执行→事件回传→停止回收→安装卸载→协议安全"全链路 |

**总计**：6 个测试套件、**121 条用例全部通过**，发现 2 个中级缺陷（D-1、D-2）、2 个低级缺陷、2 项信息级建议。
